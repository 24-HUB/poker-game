# M2 Poker Sessions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Use superpowers:subagent-driven-development only if the user selects delegated execution. Steps use checkbox syntax for tracking.

**Goal:** Two to six authenticated friends can play consecutive no-limit Texas Hold'em hands, reconnect to their private view, and end a session with correct chip results.

**Architecture:** Extend the existing Nest room registry and its single queue per room. A new pure TypeScript poker engine computes transitions; the server owns clocks, random decks, authorization, and persistence. Persist completed hands through a settlement transaction before advancing, and deliver recipient-specific snapshots through the existing Socket.IO connection.

**Tech Stack:** Existing pinned pnpm/TypeScript workspace, NestJS/Express, Socket.IO, MongoDB official driver with replica-set transactions, Next.js App Router, Zustand, Vitest, Jest, and Playwright. No framework upgrades or new runtime poker dependency are proposed.

**Spec:** `plan.md` sections 3, 8–14, 16–17. Read `AGENTS.md`, `apps/web/AGENTS.md`, `design.md`, and `CHECKPOINT.md` before execution. This document turns the M2 requirements into tasks; it does not authorize application implementation or deployment.

## Rules proposed for approval before implementation

These retain the proposals in the design and fill gaps needed for deterministic tests. Approval of this planning change does not silently confirm these gameplay defaults.

| Topic | Proposed M2 behavior |
|---|---|
| Session | 2–6 seated accounts; 1,000 chips each; fixed 10/20 blinds; integer chips |
| Timing | 30-second turn; check on timeout when legal, otherwise fold; five-second committed-result interval |
| Seat lock | Freeze participants at start; reject new joins with `SESSION_IN_PROGRESS` and show “Try again after this session”; no waiting-list subsystem or table access for invitees |
| Bust-out | Remain an authorized observer until session end; no refill or re-entry |
| Ending | Host requests end, honored after the current settlement; automatically end below two funded players; room returns to waiting |
| Leaving | Preserve the active participant's seat/stack, detach that account's room connections, and use ordinary turn timeouts; a deliberate leave removes room membership only at session end; authenticated return before then cancels pending departure |
| Disconnection | Presence counts accounts across tabs; transfer host to the lowest-seat connected participant; abort after all participants are absent for two minutes, resolving uncertain settlement first |
| Dealer | First button is lowest occupied seat; subsequent button moves clockwise to next funded participant; heads-up button posts small blind and acts first preflop, other player acts first postflop |
| Cards/showdown | Server supplies a shuffled 52-card deck; burn before flop/turn/river; reveal all non-folded contenders at contested showdown, including side-pot contenders; reveal none on an uncontested win |
| Payout | Return unmatched excess before pot splitting; exclude folded players from eligibility; split each pot separately; odd chips go clockwise starting left of button among tied winners |
| Raises | `raiseTo` means total street contribution; full minimum raise uses previous full increment; short all-ins do not alone reopen prior action; cumulative short increases reopen when the amount faced since that player's last action reaches a full raise |
| Restart | Abort interrupted sessions/hands, release participation, retain committed results; do not resume decks or award historical M2 tickets later |

## Global constraints

- Backend alone determines cards, chips, legal actions, timing, winners, and session transitions.
- One queue per room covers room mutations, game commands, timeouts, hand boundaries, settlement resolution, and abandonment. Never recursively enqueue and await the same queue.
- Engine imports neither app nor transport contracts. Browser imports contracts, never internal engine/server state.
- Use safe integers and reject invalid, fractional, negative, overflowing, or client-supplied identity/outcome fields.
- Preserve existing explicit tab takeover, auth revalidation, boot fencing, queue limit 100, 16 KiB message bound, and account rate limits.
- Transactions use the existing `TransactionRunner`; fence lifecycle writes, pass one `ClientSession` sequentially, and emit only after commit. Freeze IDs, decks, timestamps, and settlement candidates outside retryable callbacks.
- Ordinary actions remain in memory. A committed hand and session stack snapshot are durable; no deck or folded cards enter documents/logs.
- Start on a clean task branch from freshly fetched `origin/dev`; preserve unrelated changes. Each implementation task's follow-ups update its PR targeting `dev`; the user merges manually.
- Use pnpm 10.33.0 and the committed lockfile. No production migrations, provider provisioning, deployment, or paid upgrades without separate authorization.

## Review focus

1. Short blinds, repeated short all-ins, and heads-up rotation: legal action remains correct (Tasks 2–3).
2. Timeout/manual action at the same deadline and stale callbacks: exactly one transition wins (Task 5).
3. Commit succeeds but notification/reply is lost: one payout and no premature next hand (Task 6).
4. Revoked sessions, observer tabs, and reconnect: no cross-account cards or unauthorized mutation (Tasks 5, 7–8).
5. End/leave/abandon/restart races: completed results survive and participation is released exactly once (Tasks 4, 6–7).

Use these shared names across tasks:

- `PokerAction = { type: 'fold' | 'check' | 'call' } | { type: 'raise'; raiseTo: number }`. An all-in uses call or raise with the server-provided maximum; no ambiguous delta amount.
- `GameCommand` is a strict Zod union: `session:start`, `session:end`, `game:action`, `game:sync`. Mutations inherit UUID `commandId`, `authorityBootId`, `issuedAt`, `roomId`, and `controlEpoch`; end adds `sessionId`; action adds `sessionId`, `handId`, `expectedGameVersion`, and `action`; sync carries only `roomId`.
- `GameReply = { game: GameView | null; outcome: CommandOutcome | null }`; `CommandOutcome = { commandId: string; sessionId: string; handId: string | null; acceptedGameVersion: number | null }`. Cache outcome identity, then freshly project a view; never replay a snapshot containing obsolete authorization/control data.
- `GameView` includes room/boot/session identity, `handId: string | null`, `snapshotRevision`, `gameVersion`, session/hand phase, public participants/stacks/street contributions, board/pots/button, actor, `serverTime`, `deadline: string | null`, recipient's `holeCards`, showdown-only `revealedCards`, legal actions, control lease, and nullable committed hand/session results. Legal actions expose `canFold`, `canCheck`, `callAmount`, and nullable `{ minRaiseTo, maxRaiseTo, shortAllInOnly }`; no cards for outsiders.
- Engine types: `Card` is an integer 0–51; `EngineSeat` contains `accountId`, seat, and starting stack; `HandState` is internal immutable state. `EngineTransition = { state: HandState; settlement: EngineSettlement | null }`. `EngineSettlement` contains participants' contributions/payouts/final stacks/manual-action flags and permitted showdown reveals, but no timestamp or database ID.
- `startHand(input: { seats: EngineSeat[]; buttonSeat: number; smallBlind: number; bigBlind: number; deck: readonly Card[] }): EngineTransition`; `legalActions(state: HandState, accountId: string): LegalActions`; `applyAction(state: HandState, accountId: string, action: PokerAction, source: 'manual' | 'timeout'): EngineTransition`. Engine defines its own structurally compatible action/legal types; server maps explicitly.
- `GameService.execute(context: RoomContext, command: GameCommand): Promise<Result<GameReply>>` uses the existing verified identity type and registry. Queue-internal helpers do not enqueue again.
- `SettlementCandidate` freezes room/session/hand/authority identity, expected hand revision, rules version, completion time/UTC date, and engine results. `SettlementService.commit(candidate: SettlementCandidate): Promise<CommittedHandResult>` resolves retries by hand ID and verifies the candidate matches any existing receipt.
